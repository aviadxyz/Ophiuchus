# Med Bot API integration

All endpoints require `Authorization: Bearer <server-only-token>`. A token maps to exactly one astronaut on the server. Session IDs, client context, mood labels and messages never establish identity or clinical approval. Use an authenticated trusted proxy so a browser never receives the service token.

## Routes

| Method | Path | Input / result |
|---|---|---|
| POST | `/api/medbot/chat` | Typed chat request → reply, intent, tentative mood, sources, actions and safety state |
| GET | `/api/medbot/sessions/{session_id}` | Current authorized session messages, explicit preferences and consent |
| DELETE | `/api/medbot/sessions/{session_id}` | Delete that chat session |
| GET / PATCH | `/api/medbot/consent` | Read/update the authenticated astronaut's three consent flags |
| POST | `/api/medbot/mood-checkin` | Explicit voluntary check-in; requires mood-history consent |
| GET | `/api/medbot/mood-history?days=30` | Up to 100 consented check-ins; days must be 1–30 |
| DELETE | `/api/medbot/mood-history` | Delete saved mood history |
| DELETE | `/api/medbot/data` | Delete all this astronaut's Med Bot data and reset consent |
| POST | `/api/medbot/support-request` | Returns `not_configured`, `contacted: false` |
| POST | `/api/chat` | Adapter for the existing screen's request/response contract |

Full Pydantic schemas and enums are in `/docs` and `/openapi.json` on the running service.

### New chat API

First message (no session ID yet):

```json
{
  "request_id": "unique-client-message-id",
  "message": "I feel lonely today.",
  "self_reported_mood": "lonely",
  "reply_mode": "standard"
}
```

Send the returned `session_id` on follow-ups, with a new `request_id`. Preserve request ID and payload for transport retries. Request messages are limited to 4,000 characters. Optional `screen_id` identifies context but conveys no permission. `formal_assessment` defaults false and must reflect a deliberate user confirmation, not model intent.

The result contains:

```json
{
  "session_id": "server-issued-session-id",
  "message_id": "server-issued-message-id",
  "intent": "mental_health_support",
  "mood_assessment": {
    "label": "lonely",
    "source": "self_report",
    "confidence": "high",
    "user_confirmed": true
  },
  "reply": "Illustrative only: the actual reply is generated by local Ollama.",
  "sources": [],
  "suggested_actions": [],
  "safety_status": "normal",
  "human_support_available": false,
  "support_status": "not_configured",
  "forward": false,
  "limitations": [],
  "assessment_id": null,
  "generated_at": "2026-11-15T10:00:00Z"
}
```

Render replies and source excerpts as text, never injected HTML. `sources` contains actual evidence ID, title, URL, excerpt, original review status, research-only flag and limitations. Show unreviewed research labels visibly. Only allow HTTP(S) evidence links. `suggested_actions` can contain only retrieved approved/support or existing recommendation references; do not turn research text into a treatment-start control.

Show inferred mood as tentative and permit correction through `self_reported_mood` on the next message. Do not describe `confidence` as a clinical probability. Source badges and privacy controls should use existing shared components when UI work is authorized.

### Consent and mood check-ins

Consent update, either PATCH `/api/medbot/consent` or the chat request's optional `consent` object:

```json
{ "personal_health": true, "save_conversations": false, "mood_history": false }
```

Use explicit controls explaining each permission; do not enable health access just because a person mentions poor sleep or stress. Saved mood history is separate from chat saving. To submit a check-in, first enable `mood_history`, then POST:

```json
{
  "request_id": "unique-mood-checkin-id",
  "mood": "stressed",
  "intensity": 3,
  "note": "Optional voluntary note"
}
```

`intensity` is optional and must be an integer from 1–5. Optional `timestamp` must include a timezone, cannot be in the future and must be within the last 30 days. Omitting it uses server UTC. Check-ins are self-reports, not inferred diagnoses. This API does not silently write into the frontend's shared `MoodCheckin` records; their score/tag schema differs and requires separate integration approval.

### Human support

POST `/api/medbot/support-request` accepts `recipient` (`crew_medical_officer`, `flight_surgeon`, `behavioral_health_professional`, `onboard_emergency_contact`), optional `session_id`, `summary`, and `consent_to_share`.

There is no external contact integration. Display `not_configured`; never label the request sent, delivered or acknowledged. An urgent chat response should immediately surface the app's Emergency screen. No ordinary support-request button replaces that workflow. Earth communication may be delayed.

## Existing screen compatibility and future changes

The current app sends `{message, screenId, screenLabel, context, replyMode}` to `VITE_CHAT_URL` and expects `{reply, urgent, forward}`. `/api/chat` accepts exactly that shape. It returns only those three fields and uses an HttpOnly, SameSite=Strict session cookie for continuity. It ignores free-text `context` as a source of identity, consent and medical readings; authorized structured health tools supply personal data instead. The richer API is needed for mood metadata, check-ins, source panels and explicit consent controls.

Connecting the current screen still requires work **outside `Med bot`**, which has not been done or authorized by this delivery:

1. A trusted same-origin application proxy must authenticate the active user and map that session to a server credential. The current screen has no backend bearer authentication. Do not put a secret into `VITE_CHAT_URL` or the browser bundle.
2. Set the existing `VITE_CHAT_URL` to that proxy's `/api/chat` route. Forward the session cookie and authenticated requests; set `MEDBOT_SECURE_COOKIE=0` only for localhost HTTP testing.
3. Update the existing eight-second frontend timeout if local-model latency requires it. The backend uses bounded calls but cannot guarantee an eight-second cold-start response. The current UI falls back to its own scripted replies on 503/timeouts; those existing frontend fallbacks have not been changed or endorsed as source-backed answers.
4. For all new features, connect `/api/medbot/chat` instead and expose the three consent controls, mood corrections/check-ins, source links, session deletion and error states using the existing design system and shared data boundaries. Clear session/UI state when changing profiles. Do not infer a backend identity from an arbitrary browser profile ID.
5. An existing frontend "Send to flight surgeon" action records a local demonstration alert. It is not confirmed human contact and must retain its existing demo disclosure. The new backend's support request is explicitly unconfigured.

No shared contract, app source, recommendation source or ingestion file was edited. Any frontend/proxy integration should be separately approved, following the repository lane rules.

## Errors and safety states

- 401: missing/invalid server credentials; do not retry with guessed identities.
- 403: wrong session owner, ambiguous credentials, or missing required mood consent.
- 404: session missing/expired; start a new session and say prior context is unavailable.
- 409: changed payload under a reused retry key, invalid timestamp, or temporary session capacity reached.
- 422: invalid request schema; errors omit rejected sensitive values.
- 503 with `safety_status: service_unavailable`: local model failure; preserve the explicit unavailable state.

HTTP 200 may have `response_withheld` when generated content fails validation. Do not substitute invented medical advice. `urgent` is a safety state, not a diagnosis. Display it even when there are no suggested actions and no human contact integration. All data responses use `Cache-Control: no-store`.
